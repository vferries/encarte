# Encarté 1.1.0, sub-project B "Organisation" — Design Spec

- **Date:** 2026-10-06
- **Status:** Draft, pending review
- **Parent specs:** `2026-10-03-encarte-design.md`, `2026-10-05-encarte-v1.1-design.md` (sub-project A, which defines release 1.1.0 and its finalization step in §6)

## 1. Context and goals

Release 1.1.0 is built in three sub-projects. A "At checkout" is done (origin/main 2c9c01f). This spec covers **B "Organisation"**: card groups, a home-screen widget and app shortcuts. C "Migration" comes next. `v1.1.0` is tagged only after the finalization step.

Goals:
- **Groups** keep a growing collection tidy, and survive a round trip through Catima, which has groups.
- **The widget and the app shortcuts** open the right card at checkout in one tap, without going through the list.

Decisions taken with the user (2026-10-06):
- **Groups are filter chips** above the list. A card can be in several groups, as in Catima.
- **Cards are put in groups** one at a time from the card editor, or in bulk from a per-group checklist screen.
- **The widget** is a grid of cards whose source, chosen when it is placed, is either the favorites or one group. Several widgets can coexist.
- **App shortcuts:** a long press on the app icon shows up to 3 cards and "Add a card". No "pin this card" action: the widget covers it.
- **App lock and the home screen:** when the app lock is on, the widget and the shortcuts show no card or group name (option "B, hide everything").
- **Widget technology:** `RemoteViews` with `androidx.core:core-remoteviews` (option A).
  - **Glance was measured** on a minified release build (2026-10-06): +163 KB, but WorkManager adds 3 permissions (`RECEIVE_BOOT_COMPLETED`, `WAKE_LOCK`, `FOREGROUND_SERVICE`), about fifteen components and a second copy of Room.
  - **The deprecated `RemoteViews.setRemoteAdapter(int, Intent)`** is not an option.
- **Opening a card from the widget or a shortcut** behaves like a fresh launch: an unsaved edit in progress is lost.

Success criteria:
1. Upgrading from sub-project A keeps every card and photo, with no groups. A migration test proves it.
2. An Encarté → Catima → Encarté round trip keeps the groups, empty ones included, and the memberships.
3. With the app lock on, no store or group name is visible outside the app: widget, shortcut menu or pinned shortcut.
4. The merged release manifest gains **no permission** over sub-project A, and `verifyNoNetworkPermission` stays green.

## 2. Data

**`CardGroup`** (table `groups`):
- `id: Long`, auto-generated;
- `name: String`, stored trimmed.

**`CardGroupCrossRef`** (table `card_groups`):
- `cardId: Long` and `groupId: Long`, together the primary key;
- both are foreign keys with `ON DELETE CASCADE`, to `cards.id` and `groups.id`;
- an index on `groupId`.
- Deleting a card removes its memberships. Deleting a group removes its memberships and **never deletes a card**.

**Name rules:**
- A name is trimmed and must not be blank. There is no length limit: chips and widget headers end long names with "…".
- **Two groups clash** when their names have the same key: trimmed, NFD with combining marks removed, lowercased with `Locale.ROOT`.
  - "Courses", "courses" and "Coursès" clash.
  - "🛒" and "👕" do not.
  - Punctuation and symbols are kept, unlike `normalizedForMatching`, which would reduce every emoji-only name to the same empty key.
- The repository enforces both rules inside a write transaction. Create and rename return a result: `Saved`, `Blank` or `Duplicate`.

**Order:** groups are sorted by name with the card list's collator (`cardCollator()`). There is no manual order. Catima's export does not carry one either.

**Repository operations** (a new `GroupRepository`, sharing the database with `CardRepository`):
- observe the groups, sorted;
- observe the memberships, as `Map<Long, Set<Long>>` (card id → group ids);
- create, rename and delete a group;
- set one membership: used by the checklist screen;
- replace a card's set of groups: used by the editor, in the same transaction as the card's save.

## 3. Database migration 2 → 3

- `EncarteDatabase` moves to `version = 3`, with a **Room auto-migration from 2 to 3**. It only creates the two tables and the index.
- The exported schema `app/schemas/…/3.json` is committed next to `1.json` and `2.json`.
- **Migration test,** with the existing `MigrationTestHelper` setup:
  1. create a v2 database;
  2. insert cards with every v2 column filled;
  3. migrate;
  4. check every value unchanged, and both new tables empty;
  5. check that the DAOs read the rows, and that deleting a card cascades to its memberships.

## 4. Catima import and export

Catima's v2 CSV has a groups section (header `_id`, one group name per row) and a mapping section (header `cardId, groupId`, where `groupId` is the group's name). See the parent spec §11.1.

**Export:**
- The groups section lists every group, in Encarté's order. Empty groups are included.
- The mapping section has one row `cardId, groupName` per membership. `cardId` is the same id as in the cards section.

**Import, v2 files:**
- `CatimaCsv.read` returns the cards, the group names and the mappings. Today it returns only the cards.
- **Each group name in the file** is matched to an existing group by its key (§2), or created. A blank name is skipped and logged.
- **Memberships are applied to imported cards only.** A card skipped as a duplicate keeps its current groups, consistent with "a duplicate is not touched".
- **A mapping to a group missing from the groups section** still creates that group, when the mapping is applied: a mapping of a skipped duplicate creates nothing.
- **A malformed group row or mapping row** is skipped and logged. It never fails the import.
- **A mapping to an unknown `cardId`** is ignored and logged.
- Groups and memberships are written in the same transaction as the cards.

**Import, v1 files:** no groups, as today.

**Tests:**
- reading and writing both sections, with names that need CSV quoting (comma, quote, emoji);
- the mapping of names to existing groups;
- duplicates left untouched;
- orphan mappings;
- the round trip, with an empty group;
- a Catima fixture with groups.

## 5. Screens

All new dialogs and menus use the lock-aware wrappers in `core/ui/CoverableWindows.kt`, and the guard test keeps enforcing it.

### 5.1 Card list

**Chip row**, below the search field, scrolling horizontally:
- `Toutes` / `All`, then one chip per group, then `＋ Nouveau groupe` / `＋ New group`.
- With no group at all, only `＋ Nouveau groupe` is shown.

**Filter:**
- Single selection. A group filters the three sections (favorites, others, archived) to its members.
- The search combines with the filter: a card must match both.
- The selected group lives in the view model's `SavedStateHandle`. It survives rotation and process death, and a cold start begins on `Toutes`. If the selected group is deleted, the selection goes back to `Toutes`.

**Empty group:**
- Message: "Aucune carte dans « Courses »" / "No cards in "Courses"".
- Button: "Choisir les cartes" / "Choose cards", which opens §5.2.

**Long press on a group chip** opens a menu:
- **"Choisir les cartes" / "Choose cards"** opens §5.2.
- **"Renommer" / "Rename"** opens a dialog "Renommer le groupe" / "Rename group".
  - The name field is prefilled, with the buttons "Renommer" / "Rename" and "Annuler" / "Cancel".
  - Errors show under the field: "Saisissez un nom" / "Enter a name" and "Ce groupe existe déjà" / "This group already exists".
- **"Supprimer" / "Delete"** asks for confirmation.
  - Title: "Supprimer « Courses » ?" / "Delete "Courses"?".
  - Text: "Les cartes ne sont pas supprimées." / "The cards are not deleted."
  - Buttons: "Supprimer" / "Delete" and "Annuler" / "Cancel".
- The long-press action is exposed to accessibility services, with the label "Options du groupe" / "Group options".

**`＋ Nouveau groupe`** opens a dialog "Nouveau groupe" / "New group".
- The name field is labelled "Nom du groupe" / "Group name", with the buttons "Créer" / "Create" and "Annuler" / "Cancel". The errors are the same as for renaming.
- Creating the group opens §5.2 for it right away, which is the bulk-organisation flow.

**Adding a card while a group is selected:** the editor opens with that group pre-checked. `ScannerKey` and `CardEditKey` carry an optional `groupId`. Without it, the new card would seem to vanish from the filtered list.

### 5.2 "Choose cards" screen (new)

- **Navigation key:** `GroupCardsKey(groupId)`.
- **Top bar:** the group name and a back arrow.
- **Search field:** the same matching as the list.
- **Rows:** every card, sorted by name, archived cards last. Each row has a color dot, the store name and a checkbox.
- **Each tick is written immediately,** like the favorite star. There is no Save button and no discard dialog: unticking undoes a tick.
- If the group is deleted while the screen is open, the screen closes.

### 5.3 Card editor

- A new "Groupes" / "Groups" section, after the color and before the note, holds:
  - one checkable chip per group (multiple selection);
  - a `＋ Nouveau groupe` chip, with the same dialog as §5.1. The new group is created at once and checked.
- **The memberships are part of the edit:**
  - they are saved with the card, in the same transaction;
  - they are discarded with it;
  - they are restored after process death through the `SavedStateHandle`, like the other fields.
- A group created from the editor stays if the edit is discarded. An empty group is legitimate.

### 5.4 Unchanged

The card display and the settings screen.

## 6. Home-screen widget

**Rendering:**
- An `AppWidgetProvider` builds `RemoteViews`. The grid is a `GridView` (`numColumns="auto_fit"`, column width about 96 dp, resizable) filled through `RemoteViewsCompat.setRemoteAdapter(context, views, appWidgetId, viewId, RemoteCollectionItems)` from `androidx.core:core-remoteviews:1.1.0`.
- **Header:**
  - "★ Favoris" / "★ Favorites", or the group name;
  - tapping it opens the app on the list.
- **Tiles:**
  - a rounded rectangle in the card's color, with the store name in `CardPalette.contentColorFor` that color;
  - each tile's content description is the store name;
  - no photo: bitmaps in `RemoteViews` are size-limited, and file URIs would have to be shared with the launcher;
  - no expiry badge;
  - the system font: `RemoteViews` layouts do not use the app's Nunito font resource.
- **Content:** the source's non-archived cards, in the list's order (the sort setting, favorites first for a group).
- **Empty source:**
  - "Aucune carte favorite" / "No favorite cards", or "Aucune carte dans « Courses »" / "No cards in "Courses"";
  - tapping opens the app.
- **Light and dark:** backgrounds and header colors come from `values` / `values-night` resources.
- **Widget picker:**
  - `previewLayout` and `description` on Android 12+: "Vos cartes favorites ou un groupe, à portée de main." / "Your favorite cards or a group, one tap away.";
  - older versions show the app icon.
- **`updatePeriodMillis = 0`:** data only changes inside the app.

**Configuration:**
- **`WidgetConfigActivity`** (Compose, the app theme) is the provider's configure activity.
  - Title: "Afficher dans le widget" / "Show in the widget".
  - Choices: "★ Favoris" / "★ Favorites", then the groups.
  - Choosing one saves the source, updates the widget and finishes with `RESULT_OK`. Back finishes with `RESULT_CANCELED`, so the launcher drops the widget.
- **It sits behind the same lock as the app,** since it shows group names.
  - The lock wiring now in `MainActivity` (lock state, device-secure check, prompt, `LockGate`, `SecureWindowEffect`) moves into a shared composable in `lock/`, used by both activities.
  - `WidgetConfigActivity` extends `FragmentActivity` for `BiometricPrompt`.
- **Reconfiguring later:** `widgetFeatures="reconfigurable"` (Android 12+) lets the user change the source from the widget's long-press menu.
- **Storage:** each widget's source goes in a dedicated DataStore (`widgets`), keyed by `appWidgetId`.
  - The value is `favorites` or `group:<id>`.
  - `onDeleted` removes the entry. `onRestored` moves entries to the new ids.
  - A widget with no entry, or whose group no longer exists, shows the favorites.

**App lock on:** the widget shows only "Encarté" with the lock icon, and no grid. Tapping it opens the app.

**Taps:**
- The grid uses one mutable template `PendingIntent` (explicit component), and each tile sets a fill-in intent carrying its card id.
- The header and the locked or empty states use immutable `PendingIntent`s.
- See §8 for what the intents do.

**Updates:**
- `onUpdate` (on placement, after a reboot, after an app update) renders from the database with `goAsync()`, so it works even when the process was dead.
- While the process runs, `LauncherSync` (§9) re-renders every widget whenever its inputs change.

## 7. App shortcuts

**Static shortcut "Ajouter une carte" / "Add a card":**
- Declared in `res/xml/shortcuts.xml` with the `…action.ADD_CARD` intent (§8).
- Its icon is `ic_shortcut_add`, an adaptive icon built from the `ic_add` path: navy on the launcher icon's cream background. The white `ic_add` alone would be invisible on the white disc that launchers draw behind shortcut icons.
- It stays when the app lock is on: the app then opens behind the lock.

**Dynamic card shortcuts:**
- **Up to 3 cards,** so the menu holds at most 4 entries with the static one. It never exceeds `ShortcutManagerCompat.getMaxShortcutCountPerActivity` minus the static shortcuts.
- **Ranking:** non-archived cards only, favorites first, then by `lastUsedAt` descending (never-used last), then by name with the collator.
- **Shortcut id:** `card:<id>`.
- **Label:** the store name, as both the short and the long label.
- **Icon:** an adaptive bitmap generated from the card. Its background is the card's color, and its foreground is the store name's first character (code point), uppercased, in Nunito, colored with `CardPalette.contentColorFor`, inside the adaptive-icon safe zone.
- **Intent:** `…action.VIEW_CARD` with the card id (§8).
- `LauncherSync` calls `ShortcutManagerCompat.setDynamicShortcuts` only when the computed list changed, which stays clear of Android's rate limit. If the call returns `false`, it logs and retries at the next change.

**App lock on:**
- **Dynamic card shortcuts** are removed.
- **Pinned card shortcuts** (a user can drag a menu entry onto the home screen, and the app cannot remove it) are updated with `updateShortcuts` to the label "Encarté" and the app icon. They still open the card, behind the lock.
- **When the lock is turned off,** their store names and icons come back.

**Card deleted:** its pinned shortcut is disabled with `disableShortcuts`, with the message "Cette carte a été supprimée" / "This card was deleted".

## 8. Opening from outside

`MainActivity` handles two explicit actions:
- **`io.github.vferries.encarte.action.VIEW_CARD`** with a `card_id` extra (`Long`). The back stack becomes `CardListKey → CardDisplayKey(id)`, so Back returns to the list.
- **`io.github.vferries.encarte.action.ADD_CARD`.** The back stack becomes `CardListKey → ScannerKey`.

**Launching:**
- Both are launched with `FLAG_ACTIVITY_NEW_TASK | FLAG_ACTIVITY_CLEAR_TASK`, like a fresh launch. Launchers already do this for shortcuts, so the widget behaves the same way.
- An unsaved edit in progress is lost (decided in §1).

**Reading the intent:**
- `MainActivity` reads the intent only when `savedInstanceState == null`. A restore after process death keeps the saved back stack.
- `EncarteNavHost` takes the initial keys as a parameter.

**Edge cases:**
- **A missing or invalid `card_id`** (zero, negative, absent) opens the list only, and is logged.
- **A card deleted since the widget or shortcut was rendered** opens the card display's existing "Cette carte n'existe plus." / "This card no longer exists." state. Back returns to the list.

**Lock and NFC:** nothing changes.
- The activity opens behind `LockGate`, and the card shows once unlocked.
- The contactless block applies as usual.
- Another app sending these intents can only open a screen behind the lock, and no data leaves the app.

## 9. `LauncherSync`

An app-scoped component, started from `EncarteApp.onCreate`, keeps the widgets and the shortcuts in step with the data.

- **Inputs** (combined flows):
  - the cards;
  - the groups and memberships;
  - `lockEnabled`;
  - the sort order;
  - the widget sources.
- **Pure functions,** unit-tested on the JVM:
  - `shortcutCards(cards, collator, limit)` gives the ranked cards for §7;
  - `widgetContent(source, cards, groups, memberships, order, locked)` gives a header, the tiles, and an empty or locked state for §6.
- **Ports,** each with a real implementation and a fake for tests:
  - a `ShortcutPublisher` wraps `ShortcutManagerCompat`: set dynamic shortcuts, update pinned ones, disable ones;
  - a `WidgetRenderer` wraps `AppWidgetManager` and the `RemoteViews` building.
- **Deduplication:** each output is compared with the last one pushed (`distinctUntilChanged`), so an unrelated change, such as `lastUsedAt` on a card outside the top 3, pushes nothing.
- **Error handling:** a failure while pushing is logged and does not stop the collection. The next change tries again.
- **Card deletion:** each sync compares the launcher's pinned card shortcuts with the current cards, and disables those whose card is gone (§7). This also catches a deletion made while the sync was not running.

Like A, sub-project B does **not** bump the version or tag.

**Dependency:** `androidx.core:core-remoteviews:1.1.0`, approved by the user on 2026-10-06.
- Apache 2.0, fine for F-Droid.
- Its only dependencies are `androidx.core`, `androidx.annotation` and the Kotlin stdlib.

- **Shortcuts:**
  - long-press the app icon: up to 3 cards and "Add a card" are shown;
  - drag a card onto the home screen, then turn the lock on: the menu keeps only "Add a card", and the pinned shortcut reads "Encarté".

## 11. Out of scope

- Photos and expiry badges in the widget.
- "Pin this card" from the app.
- A single-card widget.
- Per-group shortcuts.
- Manual group order, nested groups, group colors or icons.
- Showing a card's groups on the card display.
- `reportShortcutUsed`.
- Lock-screen or hub widgets.
- A per-group sort order.
- FidMe, pkpass and PDF import: sub-project C.
- The version bump, changelogs, store descriptions and screenshots: the finalization step (sub-project A spec, §6).
