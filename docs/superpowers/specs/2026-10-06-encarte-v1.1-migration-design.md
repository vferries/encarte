# Encarté 1.1.0, sub-project C "Migration" — Design Spec

- **Date:** 2026-10-06
- **Status:** Draft, pending review
- **Parent specs:** `2026-10-03-encarte-design.md`, `2026-10-05-encarte-v1.1-design.md` (sub-project A, which defines release 1.1.0 and its finalization step in §6), `2026-10-06-encarte-v1.1-organisation-design.md` (sub-project B)

## 1. Context and goals

Release 1.1.0 is built in three sub-projects. A "At checkout" and B "Organisation" are done (origin/main b3308e9). This spec covers **C "Migration"**: getting cards into Encarté without retyping them. `v1.1.0` is tagged only after the finalization step.

Goals:
- **FidMe users can move to Encarté.** FidMe is the most widely used loyalty-card app in France.
- **Cards delivered as files can be imported:** a Wallet pass (`.pkpass`) received by email, or a PDF holding a barcode.

Catima already imports these three formats. Its implementation was read on 2026-10-06 (main 4f591f9) to learn the formats and their pitfalls. No code is copied.

Decisions taken with the user (2026-10-06):
- **FidMe exports no barcode type.** Encarté **guesses** it from the number and tells the user to check (option A).
- **Entry points (option B):**
  - in the app, through the scanner;
  - from other apps, a `.pkpass` through "Open with" and "Share", and a PDF through "Share" only.
- **Two paths (option 1):**
  - **FidMe** is a batch import through the existing backup import;
  - **a pass or a PDF** gives one card at a time, through the **pre-filled card editor**, as after a scan. A chooser comes first when a PDF holds several codes.
- **Tickets** (concerts and similar) work through the same paths as a side effect. They get no dedicated treatment and are not advertised.
- **The user has no FidMe account,** so the FidMe format comes from Catima's implementation and test fixture (2021). It must be checked on a real export as soon as one is available (§8).

Success criteria:
1. A FidMe export in the documented format imports in one go:
   - rows without a number are skipped and counted;
   - duplicates are skipped and counted;
   - every imported card gets a guessed barcode type.
2. A `.pkpass` opened from another app, or picked in the scanner, opens the editor pre-filled. The saved card's barcode is the pass's barcode.
3. A PDF with one code opens the pre-filled editor. A PDF with several codes offers a chooser that shows them drawn.
4. No new dependency, and **no new permission** in the merged release manifest compared with sub-project B. `verifyNoNetworkPermission` stays green.

## 2. Shared pieces

**`CardDraft`** (`@Serializable`), what an import hands to the editor. Every field is optional:
- `storeName: String`, `cardNumber: String`;
- `barcodeValue: String?`: the encoded value when it differs from `cardNumber`;
- `barcodeFormat: BarcodeFormat?`, `color: Int?`;
- `expiresOnEpochDay: Long?`: `LocalDate` has no serializer, and an epoch day keeps the key small;
- `note: String`;
- `notice: DraftNotice?`.

`DraftNotice` has one value, `PASS_WITHOUT_BARCODE`.

**`CardEditKey`** gains `draft: CardDraft? = null`.
- **For a new card with a draft**, the editor pre-fills every field from it.
- **A null `color`** keeps today's rule for new cards: the brand's color if the name matches the catalog, otherwise the palette color derived from the name.
- `barcodeValue`/`barcodeFormat` (the scanner's prefill), `unsupportedFormat` and `groupId` keep their meaning.

**File kind** is detected from the content, never from the announced MIME type, which is often wrong for `.pkpass`:
- the file starts with `%PDF-`: **PDF**;
- the file starts with the ZIP signature `PK\u0003\u0004` and contains a root `pass.json`: **pass**;
- the image decoder can read it: **image** (today's image scan);
- anything else: **unrecognized**.

**`FileImport`** detects the kind of a work file and runs the matching reader. It returns an `ImportOutcome`:
- `Draft(CardDraft)`;
- `Choice(List<FoundCode>)`;
- `Image(ScannedCode?)`;
- `Failure(reason)`.

The scanner and the `ImportKey` screen (§6) both use it.

**Work files:**
- A file to analyse is first copied into `cacheDir/imports/`, under a random UUID name, with a **20 MB cap**.
- It is deleted as soon as the analysis ends, whatever the outcome.
- `AppContainer.cleanUpLeftovers` also empties the folder at startup.

## 3. FidMe import (batch)

**Entry point:** "Réglages → Importer des cartes", unchanged. Its subtitle becomes:
- FR: « Depuis une sauvegarde Encarté ou Catima, ou un export FidMe »
- EN: "From an Encarté or Catima backup, or a FidMe export"

**Detection** happens in `BackupService.import`, from the ZIP's entries:
- a `catima.csv` entry: today's Catima path, unchanged;
- otherwise, an entry named `loyalty_programs.csv`, at the root or in a folder, with any case: **FidMe**;
- otherwise: `ImportResult.Invalid`, as today.

A password-protected ZIP still goes through `PasswordRequired`. FidMe exports are not encrypted.

**Reading `loyalty_programs.csv`:**
- The entry is read whole, then decoded as UTF-8. A leading BOM is dropped. Catima decodes 1 KB chunks, which can split an accented character.
- The parser is `commons-csv` with the `;` delimiter, RFC 4180 quoting and the first record as header. Header names are trimmed and compared case-insensitively.
- `Reference` and `Retailer` are required **columns**. Without them the file is not a FidMe export, so the result is `Invalid` and the cause is logged.

**Each row:**
- **store name** ← `Retailer`, trimmed;
- **card number** ← `Reference`, trimmed;
- **a row with a blank number or a blank store name is skipped and counted, never fatal.** FidMe blanks the number of expired cards;
- **note** ← one line for `Program` if it is not blank and its `normalizedForMatching()` differs from the store name's, then one line "First Last" if either is present. `Added At` is ignored;
- the other files of the export (points, stamps, tickets, profile) are ignored.

**Guessed barcode type** (`guessBarcodeFormat(number)`, pure, in `core/barcode`):
- 13 digits with a valid check digit (`Gtin`): EAN-13;
- 8 digits with a valid check digit: EAN-8;
- 12 digits with a valid check digit: UPC-A;
- otherwise, if `BarcodeValidator.validate(number, CODE_128)` accepts it (printable ASCII): Code 128;
- otherwise: `null`, the number only.

**Card fields:**
- **color:** the brand catalog's color when `BrandCatalog.match(storeName)` finds one, otherwise `CardPalette.defaultFor(storeName)`;
- not a favorite, not archived;
- no expiry, photos or groups;
- `createdAt` = now, `lastUsedAt` = null.

**Like a Catima import:**
- duplicates are skipped and counted with `duplicateKey()`;
- the cards are written in one transaction;
- the 10 000-card cap applies to the rows read.

**Result:** `ImportResult.Success` gains:
- `skippedWithoutNumber: Int`, 0 for Catima;
- `source: ImportSource` (`CATIMA`, `FIDME`).

A FidMe success is shown in an `EncarteAlertDialog` titled « Import FidMe » / "FidMe import". It contains:
- the existing plurals for imported and duplicate cards;
- a new plural, only when it is non-zero:
  - FR: « %d ignorée sans numéro (carte expirée dans FidMe) » / « %d ignorées sans numéro (cartes expirées dans FidMe) »
  - EN: "%d skipped without a number (expired in FidMe)" / "%d skipped without a number (expired in FidMe)";
- always:
  - FR: « FidMe n'exporte pas le type de code-barres : vérifiez-les en caisse ou rescannez la carte. »
  - EN: "FidMe doesn't export barcode types: check them at checkout or rescan the card."

A Catima import keeps today's feedback.

## 4. Pass import (`.pkpass`)

**Reading** (`PassReader`, pure apart from the ZIP stream):
- The ZIP is read in memory and nothing is extracted to disk.
- Only `pass.json` and the `pass.strings` of `*.lproj` folders are read:
  - at most 512 KB each;
  - at most 64 entries examined;
  - an oversized entry makes the file unrecognized, and is logged.
- **`pass.json`** is decoded as UTF-8, with a BOM dropped, and parsed with `kotlinx.serialization.json` as a `JsonObject`. `formatVersion` must be 1.
- **Localization:** the `.lproj` folder matching the app's current language, then `en.lproj`, then none. Values of `logoText`, `organizationName` and `description` that are keys of that table are replaced by their translation.
- **`pass.strings`:**
  - **encoding:** UTF-16 when it starts with a UTF-16 BOM or contains NUL bytes, UTF-8 otherwise;
  - **syntax:** `"key" = "value";` lines with `/* */` and `//` comments, and the escapes `\"`, `\\`, `\n` and `\t`;
  - a malformed line is skipped and logged.
- **The signature and `manifest.json` are not verified:** the import is offline and the user chose the file.

**Mapping to a `CardDraft`:**
- **storeName** ← `logoText`, otherwise `organizationName`, otherwise empty.
- **Barcode:** the first entry of `barcodes[]`, then the legacy `barcode`, whose `format` is supported:

  | Pass format | Encarté format |
  |---|---|
  | `PKBarcodeFormatQR` | `QR_CODE` |
  | `PKBarcodeFormatPDF417` | `PDF_417` |
  | `PKBarcodeFormatAztec` | `AZTEC` |
  | `PKBarcodeFormatCode128` | `CODE_128` |

  - An entry whose `message` `BarcodeValidator` rejects for that format is skipped.
  - **cardNumber** ← `altText` when it is not blank, otherwise `message`.
  - **barcodeValue** ← `message` when it differs from cardNumber.
  - `messageEncoding` is not used: Encarté encodes the value as it does for any card.
- **color** ← `backgroundColor`, either `rgb(r, g, b)` with optional spaces or `#RRGGBB`, made opaque. Unparseable means null.
- **expiresOnEpochDay** ← `expirationDate`:
  - an ISO 8601 date-time with an offset, converted to a date in the device time zone;
  - otherwise a plain ISO date;
  - otherwise null, logged.
- **note** ← `description`. No other field is copied: balances and times would go stale.
- **No supported barcode:** a draft with storeName and note, an empty cardNumber, and `notice = PASS_WITHOUT_BARCODE`. The editor shows:
  - FR: « Ce pass ne contient pas de code-barres utilisable : saisissez le numéro. »
  - EN: "This pass has no usable barcode: enter the number."
- **Not used:** images, `voided`, `relevantDate`, `webServiceURL`, `locations`, `semantics`, other fields.

**Unrecognized pass** (not a ZIP, no `pass.json`, invalid JSON, `formatVersion` ≠ 1):
- FR: « Ce fichier n'est pas un pass reconnu. »
- EN: "This file isn't a recognized pass."

## 5. PDF import

**Reading** (`PdfCodeFinder`):
- The work file is opened with `ParcelFileDescriptor` and `PdfRenderer`.
- **Only the first 10 pages are read.**
- **Rendering:** each page is drawn into an ARGB_8888 bitmap on a white background, with `RENDER_MODE_FOR_DISPLAY`. It is scaled so its long side is 2 400 px, with the scale kept between 1 and 4. An A4 page is about 2.85×; Catima renders at 1×, which misses small 2D codes.
- **Each page is closed in a `finally`,** since `PdfRenderer` allows only one open page. Each bitmap is recycled after scanning.
- **A password-protected or damaged PDF** (`SecurityException`, `IOException`) is logged and reported as:
  - FR: « Impossible de lire ce PDF (protégé ou endommagé). »
  - EN: "Can't read this PDF (protected or damaged)."

**Detection:**
- `BarcodeScanner` gains `scanAll(bitmap, maxSymbols)`, which returns every usable result. The existing `scan` is unchanged.
- PDF pages use `maxSymbols = 8`.
- Each result goes through `ScanMapping`, like a camera scan.
- Results keep their page number (1-based). A result with the same format and value as an earlier one is dropped.

**Outcome:**
- **No code:**
  - FR: « Aucun code-barres trouvé dans ce PDF. »
  - EN: "No barcode found in this PDF."
- **One code:** the editor opens with a draft holding cardNumber and barcodeFormat.
- **Several codes:** the "Choose a code" screen (§6).

The store name is left for the user to type: a PDF gives no reliable one.

## 6. Entry points and navigation

**Scanner:**
- **The second button** becomes « Image ou fichier » / "Image or file", replacing « Depuis une image » / "From an image". The label stays short because both buttons already wrap at 360 dp.
- **The picker** is `ActivityResultContracts.OpenDocument` with `image/*`, `application/pdf`, `application/vnd.apple.pkpass`, `application/vnd-com.apple.pkpass` and `application/octet-stream`. The last one is how some sources label a `.pkpass`.
- **The picked file** is copied (§2), its kind detected, then analysed by the same `FileImport` code as below:
  - **image:** today's single-code scan, unchanged;
  - **pass or PDF:** the scanner is replaced by the editor or the chooser, through `replaceTopIf(ScannerKey::class, …)`;
  - **errors** show in the scanner, like today's "image not decoded" message;
  - **an unrecognized file:** « Fichier non reconnu. » / "Unrecognized file.";
  - `ScannerKey.groupId` still pre-checks the group in the editor.

**From other apps: `ImportActivity`:**
- **Manifest:** a new exported activity with a translucent, no-title theme: the window shows nothing, unless the copy is slow (see the progress card below). It carries the intent filters, all in category `DEFAULT`:
  - `VIEW` with mime types `application/vnd.apple.pkpass` and `application/vnd-com.apple.pkpass`, scheme `content`;
  - `SEND` with mime types `application/vnd.apple.pkpass`, `application/vnd-com.apple.pkpass` and `application/pdf`.
- **Behaviour:**
  - It takes the URI from `data` (VIEW) or `EXTRA_STREAM` (SEND, read with `IntentCompat.getParcelableExtra`).
  - It copies the file on `Dispatchers.IO` while the read grant is valid (§2, 20 MB cap).
  - It then starts `MainActivity` with `LaunchRequests.importFile(context, fileName)`, and finishes.
- **Progress card:** a slow provider (a file on a cloud drive) would leave an invisible window taking the touches, and the screen would look frozen.
  - If the copy is still running after 400 ms, `ImportActivity` draws, with Compose and `EncarteTheme`, a small centered card over a light scrim: a progress indicator, « Import en cours… » / "Importing…" (announced as a polite live region) and a « Annuler » / "Cancel" button. A quick import never shows it.
  - Cancel and Back cancel the copy: `ImportFiles.copy` checks between buffers whether it should go on, so the read stops, the partial file is deleted, nothing is started, and the activity finishes without a toast. The cancellation is logged, without content.
  - The card shows no card data, so the app lock is not involved.
- **Copy failure** (missing URI, `SecurityException`, `IOException`, file too large): a toast « Impossible d'ouvrir ce fichier. » / "Can't open this file.", the cause logged, then finish.
- **Why a separate activity:** with the filters on `MainActivity`, opening a pass from a mail app would start a second Encarté in that app's task. It also keeps the code exposed to other apps tiny.

**`LaunchRequests`** gains `ACTION_IMPORT_FILE` with an `EXTRA_FILE_NAME`:
- Launched like the widget's requests: `NEW_TASK | CLEAR_TASK`, read only when `savedInstanceState == null`, ignored when launched from recents.
- **The back stack** becomes `CardListKey → ImportKey(fileName)`.
- **Only a plain file name is accepted:** a UUID, no separator. It is resolved inside `cacheDir/imports/`. `MainActivity` is exported, and another app must not be able to point it at any other file. An invalid name opens the list only and is logged.

**`ImportKey` screen ("Reading…"):**
- It shows a progress indicator with « Lecture du fichier… » / "Reading the file…".
- Its view model detects the kind and analyses the file off the main thread, then deletes it.
- It then replaces itself with:
  - `CardEditKey(draft = …)`: one result;
  - `ImportChoiceKey(codes)`: several PDF codes;
  - **an image:** `CardEditKey` with the scanned code, or the "image not decoded" message;
  - **an error:** it pops back to the list and shows the error in a snackbar.
- **A missing file**, which happens after process death since startup empties the folder, is an error:
  - FR: « Ce fichier n'est plus disponible. »
  - EN: "This file is no longer available."

**`ImportChoiceKey(codes: List<FoundCode>)` ("Choose a code"):**
- `FoundCode` holds `value`, `format` and `page`.
- **Title:** « Choisir un code » / "Choose a code".
- **Each row** shows:
  - the code drawn with the existing `BarcodeImage`, or the value alone when the format is null;
  - the value;
  - « Page %d » / "Page %d", and the format's label.
- Tapping a row replaces the screen with the editor and that code's draft.
- The key carries the decoded data, not the file, so the screen survives process death.

**Lock:** everything runs behind `AppLockGate`. `ImportActivity` shows only its progress card and reads no card data. The editor and the chooser appear only once unlocked.

Arriving from another app replaces the screen in progress, as for the widget (sub-project B §8). An unsaved edit is lost.

## 8. Open points

- **The FidMe format is unverified on a real 2026 export.** The user has no FidMe account.
  - The reader follows Catima's fixture: header `Retailer;Program;Added At;Reference;Firstname;Lastname`, `;`-separated, a `loyalty_programs.csv` entry in a ZIP.
  - Our own fixture reproduces that format.
  - **If a real export differs, it is a bug to fix with that file as the new fixture.**

## 9. Out of scope

- `.pkpasses` bundles and `.espass` files.
- PDF in "Open with".
- `application/octet-stream` intent filters.
- Recognizing the store name in a PDF (OCR).
- Pass images, `voided` and online pass updates.
- Tickets as a feature (several seats at once, a tickets section, archiving after the date).
- FidMe points, stamps, tickets and images.
- Sharing plain text to Encarté.
- Card-sharing URLs.
- The version bump, changelogs, store descriptions, screenshots and FAQ: the finalization step.

## 10. Verification

**JVM unit tests:**
- **FidMe reader:** BOM, header case and spaces, quoted fields with `;`, a row without a number, a row without a store, missing required columns (`Invalid`), a nested `loyalty_programs.csv`, detection against a Catima ZIP.
- **FidMe mapping:** note lines (program equal to the store name is dropped), brand color, duplicates, the counts in `Success`.
- **`guessBarcodeFormat`:**
  - a valid EAN-13 (and the same 13 digits with a wrong check digit giving Code 128);
  - a valid EAN-8 and a valid UPC-A;
  - letters and digits giving Code 128;
  - non-ASCII giving null.
- **`PassReader`:**
  - `barcodes[]` before `barcode`;
  - unsupported formats skipped;
  - `altText` and `message`;
  - no barcode giving `PASS_WITHOUT_BARCODE`;
  - `logoText` before `organizationName`;
  - `pass.strings` in UTF-8 and in UTF-16 with comments and escapes, and the language fallback;
  - `rgb()` and `#RRGGBB` colors, a date-time with offset, a plain date and an invalid date;
  - `formatVersion` ≠ 1, a missing `pass.json`, an oversized entry.
- **Fixtures:** our own small `.pkpass` files and FidMe ZIP, built in the tests or committed under `app/src/test/resources/`.
- **File kind detection:** PDF, pass, image, a ZIP without `pass.json`, random bytes.
- **`LaunchRequests`:** `ACTION_IMPORT_FILE` accepted with a UUID name, refused with `../x`, an absolute path or an empty name.

**Instrumented test** (`connectedDebugAndroidTest`, like the existing zxing-cpp tests):
- `PdfCodeFinder` on a committed two-page test PDF holding a QR code (page 1) and an EAN-13 (page 2): both found, with their pages;
- a page beyond 10 is ignored;
- a password-protected PDF is reported as unreadable.

**Compose and Robolectric:**
- the scanner's « Image ou fichier » button and the error messages;
- the "Choose a code" screen;
- the editor pre-filled from a draft, with the pass notice;
- `ImportActivity`: it copies and relaunches, refuses an oversized file, and survives a missing URI; the progress card appears only after 400 ms; Cancel and Back stop the copy, leave no file and start nothing;
- the intent filters, through `PackageManager.queryIntentActivities`:
  - a pkpass resolves for VIEW and SEND;
  - a PDF resolves for SEND only;
- the `ImportKey` screen for each outcome, including a missing file.

**Build:**
- `./gradlew clean assembleRelease lintDebug testDebugUnitTest verifyNoNetworkPermission` is green.
- The merged release manifest's permissions are identical to sub-project B's.

**On the emulator:** the three checklist items, plus a 360 dp check of the scanner buttons, in FR and EN, light and dark.
